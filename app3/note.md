# 問卷配對平台 — MVP 規格筆記

## 0. 已定案決策

| 項目 | 決策 |
|------|------|
| 平台 | **僅 App**（不做 Web MVP） |
| 後端 | **Supabase** |
| 登入 | **Email 驗證**（magic link／OTP；MVP 不做 Google OAuth、不做手機驗證） |
| 角色 | **同一帳號可當 A 也能當 B** |
| 自領限制 | **A 不可領自己案件的獎**（`user_id === listing.publisher_id` 擋核銷） |
| 完成碼模型 | **選 A**：開始填答產生 `attempt_token` → 預填進外部表單 → 感謝頁／結尾顯示同一組碼 → B 貼回平台核銷（**token = 完成碼**） |
| 審核 | 送審後 **Email 通知營運者**人工審；無完整後台也可先用信箱＋Supabase 改狀態 |
| 禮券上傳 | **A 透過填寫表格送出**（表單欄位貼碼／逐筆輸入，非必做 CSV 檔上傳） |
| 第一刀範圍 | 先做 **「瀏覽 + 貼碼領獎」**（案件與禮券庫可先人工／營運寫入）；上架精靈、送審流程列為下一刀 |

---

## 1. 產品定位

雙邊媒合平台：

| 角色 | 說明 |
|------|------|
| **A（發布者）** | 需要他人填問卷；上架時必須鎖定獎勵 |
| **B（填答者）** | 瀏覽案件、外連填答、回填完成碼、領取獎勵 |

MVP 核心：**禮券託管 + 問卷媒合看板**（不做現金錢包、不自建完整問卷編輯器、不存問卷答案）。

技術邊界：Expo／React Native App + Supabase（Auth、DB、Storage 視需要）。

---

## 2. 獎勵（MVP 限定）

**僅支援：**

- 星巴克禮券（數位序號／兌換碼）
- 超商禮券（7-11 / 全家等數位序號）

**不做（v1）：** 現金、平台點數餘額、實體寄送、A 自行事後轉帳、其他品牌禮券（可後期擴充）。

### 託管規則

1. A 上架審核通過前／通過時，必須送出對應名額數量的禮券碼並鎖定在平台（**透過上架表單欄位送出**）。
2. 鎖定後 A 不可抽回已占用名額對應的碼（或僅在案件未開始／撤案且無人領取時依規則退回）。
3. B 完成驗證後，系統發放 **1 組未使用禮券碼**，該碼標記已發放。
4. 禮券碼加密存放；對 B 顯示時建議「僅顯示一次／可再次於領獎紀錄查看有限次數」。

> **第一刀**：禮券碼可由營運直接寫入 Supabase；完整「A 表單上傳鎖定」在上架刀再接。

---

## 3. 完成驗證：結尾完成碼 → 手動貼回（MVP）

### 定案模型（選 A）

```
B Email 登入 → 點「開始填答」→ 平台產生一次一碼 attempt_token（= 完成碼）
    → 導向外部問卷，並盡量以 URL 參數預填該 token
    → B 填完 → 表單結尾／感謝頁顯示「你的完成碼」（即該 token，或預填欄位內容）
    → B 回 App 貼上完成碼
    → 核銷成功 → 發放 1 張已鎖定禮券
```

重點：

- **完成碼 = 該次 attempt 的 token**，不是全場共用碼，也不是 A 另建的碼庫。
- A 的義務是在外部表單結尾讓 B **看得到**這個預填／帶入的 token（教學與截圖審核在上架刀強制）。

### 強制規則（防共用碼外流）

1. **禁止全場共用碼**（不可只有一個 `THANKS2026` 給所有人用）。
2. 完成碼必須為 **一次一碼（one-time）**：核銷後立即作廢，不可重複領獎。
3. 完成碼必須 **綁定案件 + 該次 attempt + B 的 `user_id`**。
4. 同一 B 對同一案件 **只能成功領獎一次**。
5. **A 不可核銷／領取自己發布案件的獎**。
6. attempt／完成碼設 **時效**（建議開始後 48 小時內須回填，可調）。
7. 公開案件頁 **不得** 展示完成碼或碼庫。
8. 領獎頻率限制 + 異常速度打標，降低被刷風險。

### A 義務：結尾一定要放碼

- 上架時 **強制** 透過「上架精靈」完成結尾設定，未完成不可送審／上架。（**第一刀先略；由營運保證測試案件已正確放碼**）
- A 必須在外部表單 **最後一頁／感謝頁** 顯示完成碼（或顯示預填的平台碼欄位內容）。
- 若因 A 未正確放碼導致 B 無法領獎：以客服／案件暫停／退款（退碼）規則處理；平台應在精靈中重複警示。

---

## 4. 上架精靈（A 必走）— 第二刀

> 第一刀不做 App 內上架；下列為完整 MVP 目標。

精靈逐步引導，缺一步不可送出：

1. **基本資訊**：標題、類型、預估填答分鐘數、簡短說明。
2. **強制欄位**（見第 5 節）全部填寫。
3. **外部問卷連結** + 表單截圖（至少含結尾／感謝頁示意）。
4. **完成碼設定教學**（不可跳過）：
   - 提供「開始填答」連結範本（含預填參數說明）。
   - 提供結尾文案範本，例如：  
     `感謝填答！你的完成碼是：{{token}}。請於 48 小時內回到平台貼上以領取獎勵。`
   - A 勾選確認：「我已在表單結尾顯示一次完成碼／平台碼欄位」。
5. **禮券碼庫**：以**表單欄位**送出（逐筆／多行貼上皆可）；數量必須 ≥（建議 =）人數上限；類型僅星巴克／超商。
6. **預覽案件頁** → 送審 → **Email 通知營運者審核**。

審核通過後獎勵維持鎖定，案件依開放天數上架。

---

## 5. 強制欄位（案件）

上架必填：

| 欄位 | 說明 |
|------|------|
| 標題 | 案件名稱 |
| 類型／分類 | 見第 7 節 |
| 預估分鐘數 | 讓 B 評估成本 |
| 開放天數 | 上架後可填期間 |
| 人數限制（名額） | 與鎖定禮券數量對齊 |
| 資格限制 | 可先自填聲明（年齡、地區、身份等）；MVP 不做實核 |
| 外部問卷連結 | Google 表單／SurveyCake 等 |
| 表單截圖 | 含結尾放碼證明，供審核 |
| 獎勵類型 | 星巴克禮券 **或** 超商禮券 |
| 單份獎勵說明 | 面額／說明文字 |
| 禮券碼清單 | **表單送出**並鎖定 |
| 完成碼結尾確認 | 精靈勾選 + 截圖 |

**審核應擋：** 違法／色情／詐騙連結、索取身分證或銀行密碼、獎勵誇大不實、未在結尾放碼、禮券數量不足。

**審核通知：** 送審成功後寄 Email 給營運者（含案件摘要與後台／Supabase 連結）；通過／退回後可再通知 A（第二刀）。

## 6. 登入系統（防刷必做）

### 為何必做

有限量高價值禮券時，未登入／無身分 = 腳本與多人共用裝置刷光名額。

### MVP 要求（已定案）

1. **A、B 皆需登入** 才能發布／開始填答／領獎（同一帳號兩種行為）。
2. **僅 Email 驗證**（Supabase Auth magic link／Email OTP）。Google OAuth、手機驗證列後期。
3. 領獎與 attempt 全程綁 `user_id`；並檢查 **不得為案件發布者**。
4. 風控下限：
   - 每案每帳號僅一碼成功領獎
   - 發布者不可領自己的案
   - 短時間大量「開始填答」限流
   - 完成碼嘗試次數上限（防亂試）
5. **不存問卷答案**；B 最小資料 = 帳號識別 + 領獎／attempt 紀錄（+ 必要風控日誌，可短留存）。

---

## 7. 問卷分類

建議類型（可多選或單選，MVP 先單選）：

- 學術／論文
- 產品／市場調查
- UX／訪談篩選
- 課程／作業（若允許）
- 其他

用途：B 瀏覽篩選；後台可依類型調整審核嚴謹度（例如醫療／金流相關後期再加嚴）。

---

## 8. 角色流程摘要

### A（完整 MVP／第二刀）

註冊登入（Email）→ 上架精靈 → 表單送出禮券碼並鎖定 → 送審（Email 通知營運）→ 通過後上架 → 查看名額／發放進度 →（到期或額滿結束）

### B（第一刀必做）

註冊登入（Email）→ 瀏覽／篩選分類 → 開始填答（產生完成碼 attempt）→ 外部填寫 → 結尾看碼 → 回 App 貼碼 → 領取星巴克或超商禮券碼（**若該案為自己發布則拒絕**）

### 第一刀範圍（Ship first）

| 做 | 不做（下一刀） |
|----|----------------|
| Email 登入 | App 內上架精靈 |
| 案件列表／詳情瀏覽（資料可先 seed／營運寫入） | A 自助送審與表單上傳禮券 |
| 開始填答 → 產生 attempt_token → 外連 | Email 審核流自動化（可先手動改 DB） |
| 貼完成碼核銷 → 發放 1 張禮券 | 完整退碼／撤案 UI |
| 擋：未登入、重複領、領自己的案、過期／已用碼 | Web |

---

## 9. 系統需存資料（MVP）

### A／案件

- 帳號（Supabase Auth）
- 案件內容（強制欄位）
- 審核狀態
- 鎖定之禮券碼庫與發放狀態
- 名額、開放時間
- 發放／退回日誌

### B（最小化）

- 帳號（登入身分）
- attempt 紀錄（token、狀態、時效、`user_id`、`listing_id`）
- 領獎紀錄（哪一案、何時、哪張碼）
- 基本風控訊號（可短留存）

### 明確不存

- 外部問卷的填答內容／答案本身

---

## 10. MVP 明確不做

- 現金、錢包、提現
- 全場共用完成碼
- 未登入即可領獎
- Web 版（僅 App）
- Google OAuth／手機驗證（第一版）
- 站內完整問卷編輯器（可後期）
- Webhook／提交後自動導向核銷（可列為下一版，優於手動貼回）
- 資格實名實核
- 複雜金流合規產品
- A 領自己案件的獎

---

## 11. 下一版可考慮（非第一刀）

- App 內上架精靈 + 表單送出禮券 + Email 審核通知
- 表單提交後導向平台自動核銷
- Typeform 等 webhook 自動發獎
- 更多禮券品牌
- 手機驗證／更強裝置指紋
- Google OAuth
- 站內問卷（驗證更強，但隱私與工程成本上升）

---

## 12. 成功標準

### 第一刀

1. 未登入無法開始填答或領獎（Email 驗證）。
2. 完成碼 = attempt token，一人一案一次；截圖共用無法大量盜領。
3. 發布者無法領自己案件的獎。
4. 核銷成功僅發放星巴克／超商禮券碼，且與鎖定庫存一致。

### 完整 MVP（含上架刀）

1. A 無法繞過精靈、無法在未鎖足夠禮券、未確認結尾放碼下上架。
2. 送審會 Email 通知營運者。
3. 禮券由 A 透過表單送出並鎖定。
4. 同上第一刀防刷與發獎一致性。
